## 一、这份文档解决什么问题

聚合版 `2.4` 提出了五级认证建议，但只停留在"列出五个等级"的层面。当前主线还缺一份能直接指导认证对象结构、审核流程、材料管理、展示规则和筛选联动的详细需求方案。

这份文档的作用是：

1. 把聚合版的五级认证建议细化成可冻结的认证类型定义
2. 明确每种认证类型需要什么材料、审核流程是什么、状态如何流转
3. 明确认证状态在档案卡、匹配列表、筛选面板中的展示规则
4. 明确认证与已冻结的 `profile_certifications` 对象的对齐关系
5. 明确"认证客户优先匹配"的筛选逻辑边界

一句话：

**本文不是再重复"要做认证"，而是把聚合版 `2.4` 细化成当前主线可冻结、可评审、可继续拆 schema 和审核流的详细方案。**

## 三、与已冻结对象的对齐

### 3.1 已冻结的 `profile_certifications` 对象

主数据模型冻结 v1 已经定义了 `profile_certifications` 的最小结构：

```ts
certification_items: Array<{
  type: 'identity' | 'education' | 'income' | 'assets' | 'marital_history' | 'health' | 'other'
  status: 'not_submitted' | 'pending_review' | 'verified' | 'rejected'
  material_refs: string[]
  reviewed_at: string | null
  reviewed_by: string | null
  review_notes: string | null
}>
```

本文在此基础上展开，不重新发明对象结构。

### 3.2 已冻结的材料语义边界

导入与资料卡冻结 v1 已经明确：

- 认证材料的 `material_refs` 只存文件引用
- 认证状态由 `certification_items[*].status` 管理，不由材料存在与否推断
- 上传认证材料 ≠ 认证通过

本文遵循这些边界。

## 四、认证类型详细定义

### 4.1 五级认证体系

聚合版提出的五级认证，本文细化如下：

| 等级 | 认证类型 key | 中文名 | 业务目的 | 适用阶段 |
|------|------|------|------|------|
| L1 基础认证 | `identity` | 身份认证 | 确认客户真实身份，防止虚假注册 | 所有客户建议完成 |
| L2 学历认证 | `education` | 学历认证 | 验证学历真实性，高净值场景核心信任要素 | 首轮补齐建议 |
| L3 经济认证 | `income` + `assets` | 经济认证 | 验证收入和资产真实性，支撑条件匹配可信度 | 递进补全 |
| L4 婚况认证 | `marital_history` | 婚况认证 | 验证婚姻状况真实性，防投诉核心手段 | 首轮补齐建议 |
| L5 健康认证 | `health` | 健康认证 | 高端服务专用，验证婚检或健康状况 | 仅高端服务 |

### 4.2 各认证类型的材料要求

#### 4.2.1 L1 身份认证（`identity`）

| 项目 | 说明 |
|------|------|
| 必要材料 | 身份证正反面照片 |
| 可选补充 | 护照首页 |
| 验证要点 | 姓名与 `full_name` 一致、照片与本人一致 |
| 自动关联字段 | `full_name`、`gender`、`birth_year_month`（可辅助校验，不自动覆盖） |
| 敏感处理 | 身份证号码不作为正式字段存储，仅作为认证材料留存 |

#### 4.2.2 L2 学历认证（`education`）

| 项目 | 说明 |
|------|------|
| 必要材料 | 学信网截图 或 毕业证照片（至少一项） |
| 可选补充 | 学位证照片、海外学历认证书 |
| 验证要点 | 学历层级与 `education_level` 一致、院校名与对应学校字段一致 |
| 自动关联字段 | `education_level`、`bachelor_school`、`master_school`、`doctor_school` |
| 特殊规则 | 多学历（本硕博）可分别提交，每个层级独立验证 |

#### 4.2.3 L3 经济认证（`income` + `assets`）

经济认证拆分为两个子类型，可独立提交：

**收入认证（`income`）**

| 项目 | 说明 |
|------|------|
| 必要材料 | 工资流水截图 或 纳税证明 或 公司开具的收入证明（至少一项） |
| 可选补充 | 股权证明、分红记录 |
| 验证要点 | 收入水平与 `monthly_income` / `annual_income` 大致匹配 |
| 自动关联字段 | `monthly_income`、`annual_income`、`income_source_type` |
| 特殊规则 | 不要求精确到元，允许区间匹配；自营收入可用营业执照 + 流水替代 |

**资产认证（`assets`）**

| 项目 | 说明 |
|------|------|
| 必要材料 | 房产证照片 或 车辆行驶证照片 或 金融资产证明（至少一项） |
| 可选补充 | 车险保单、理财账户截图、保险保单 |
| 验证要点 | 资产类型与对应字段一致 |
| 自动关联字段 | `has_property`、`property_count`、`has_vehicle`、`vehicle_brand`、`vehicle_model`、`family_asset_band` |
| 特殊规则 | 房产和车辆可分别提交；金融资产第一阶段只做材料留存，不做精确验证 |

#### 4.2.4 L4 婚况认证（`marital_history`）

| 项目 | 说明 |
|------|------|
| 必要材料 | 户口本婚姻状况页 或 离婚证照片 或 法院判决书（至少一项） |
| 可选补充 | 民政局开具的单身证明 |
| 验证要点 | 婚姻状况与 `marital_history` 一致 |
| 自动关联字段 | `marital_history` |
| 特殊规则 | 未婚客户可用户口本"未婚"状态页验证；离异客户必须提供离婚证或判决书 |

#### 4.2.5 L5 健康认证（`health`）

| 项目 | 说明 |
|------|------|
| 必要材料 | 婚检报告 或 体检报告（三个月内） |
| 可选补充 | 专项检查报告 |
| 验证要点 | 报告真实性、时效性 |
| 自动关联字段 | 无直接关联字段 |
| 特殊规则 | 仅高端服务客户需要；报告有效期建议 6 个月；过期后状态自动降级为 `expired` |

## 五、认证状态流转模型

### 5.1 状态定义

在已冻结的四状态基础上，本文建议扩展为：

| 状态 | 存储值 | 展示值 | 说明 |
|------|------|------|------|
| 未提交 | `not_submitted` | 未认证 | 初始状态，客户尚未提交任何材料 |
| 待审核 | `pending_review` | 审核中 | 材料已上传，等待审核人员处理 |
| 已通过 | `verified` | 已认证 | 审核通过，认证有效 |
| 已驳回 | `rejected` | 未通过 | 审核未通过，需重新提交 |
| 已过期 | `expired` | 已过期 | 认证曾通过但已超过有效期（仅健康认证适用） |

### 5.2 状态迁移规则

```
not_submitted
  ├─ 上传材料 → pending_review
  └─ 保持（未操作）

pending_review
  ├─ 审核通过 → verified
  ├─ 审核驳回 → rejected
  └─ 客户撤回材料 → not_submitted

verified
  ├─ 超过有效期 → expired（仅健康认证）
  ├─ 人工撤销 → not_submitted（发现造假等极端情况）
  └─ 保持（正常状态）

rejected
  ├─ 重新上传材料 → pending_review
  └─ 保持（未操作）

expired
  ├─ 重新上传材料 → pending_review
  └─ 保持（未操作）
```

### 5.3 状态迁移约束

- `verified` → `not_submitted` 只允许管理员操作，且必须填写撤销原因
- `expired` 状态只适用于 `health` 类型认证，其他类型认证无有效期限制
- 状态变更必须记录操作人和操作时间
- 驳回时必须填写驳回原因，供客户/红娘参考

### 5.4 对已冻结结构的扩展建议

在已冻结的 `certification_items` 子结构基础上，建议扩展以下字段：

```ts
{
  type: 'identity' | 'education' | 'income' | 'assets' | 'marital_history' | 'health' | 'other'
  status: 'not_submitted' | 'pending_review' | 'verified' | 'rejected' | 'expired'
  material_refs: string[]
  reviewed_at: string | null
  reviewed_by: string | null
  review_notes: string | null
  // 以下为建议扩展
  submitted_at: string | null        // 材料提交时间
  expires_at: string | null           // 认证过期时间（仅 health 类型）
  rejection_reason: string | null     // 驳回原因
  related_field_keys: string[]        // 关联的正式字段 key 列表
}
```

## 六、认证审核流程

### 6.1 审核角色

| 角色 | 权限 | 说明 |
|------|------|------|
| 所属红娘 | 上传材料、查看认证状态 | 不能自行审核通过 |
| 总部管理员 | 审核通过/驳回、撤销认证 | 认证审核的唯一决策方 |
| 系统 | 自动检测过期、自动提醒 | 不做自动审核决策 |

### 6.2 审核流程

```
红娘上传客户认证材料
  ↓
系统自动创建 certification_item，status = pending_review
  ↓
系统通知总部管理员有新的待审核认证
  ↓
管理员查看材料，核对关联字段
  ├─ 通过 → status = verified，记录审核人和时间
  └─ 驳回 → status = rejected，填写驳回原因
  ↓
系统通知所属红娘审核结果
  ↓
（如驳回）红娘可重新上传材料，重新进入审核流程
```

### 6.3 审核时效要求

| 认证类型 | 建议审核时效 | 超时处理 |
|------|------|------|
| 身份认证 | 24 小时内 | 超时提醒管理员 |
| 学历认证 | 48 小时内 | 超时提醒管理员 |
| 经济认证 | 48 小时内 | 超时提醒管理员 |
| 婚况认证 | 24 小时内 | 超时提醒管理员 |
| 健康认证 | 72 小时内 | 超时提醒管理员 |

### 6.4 第一阶段审核简化

第一阶段不要求实现的审核能力：

- 自动 OCR 识别材料内容
- 自动比对材料与字段值
- 批量审核
- 审核工作台（管理员专用界面）
- 审核 SLA 监控

第一阶段必须实现的最小审核能力：

- 管理员可查看待审核列表
- 管理员可逐项审核通过或驳回
- 驳回时必须填写原因
- 审核结果通知到所属红娘

## 七、认证在各界面的展示规则

### 7.1 展示原则

- 认证状态以标签/徽章形式展示，不占用主字段位置
- 认证材料本身不对客展示，只展示认证结论
- 未认证不等于信息不可信，只是缺少额外验证

### 7.2 各界面展示规则

| 界面 | 展示内容 | 展示形式 | 说明 |
|------|------|------|------|
| 客户列表 | 已通过的认证类型标签 | 小图标/徽章 | 最多展示 3 个最重要的认证标签 |
| 客户详情 | 完整认证状态列表 | 认证卡片区 | 每种类型一行，显示状态和操作入口 |
| 内部完整版资料卡 | 已通过的认证摘要 | 认证区块 | 列出已认证项目，标注认证时间 |
| 对客介绍版资料卡 | 已通过的认证标签 | 信任标签 | 只展示"已认证"标签，不展示材料内容 |
| 营销版资料卡 | 不展示 | - | 营销版不涉及认证信息 |
| 匹配列表 | 已通过的认证标签 | 筛选标签 | 支持"只看已认证客户"筛选 |

### 7.3 认证标签展示优先级

当空间有限时（如列表卡片），按以下优先级展示认证标签：

1. 身份认证（最基础的信任基石）
2. 婚况认证（防投诉核心）
3. 学历认证（高净值场景高频关注）
4. 经济认证（条件匹配可信度）
5. 健康认证（仅高端服务）

## 八、认证与筛选/匹配的联动

### 8.1 筛选面板

筛选面板增加认证相关筛选条件：

| 筛选项 | 类型 | 说明 |
|------|------|------|
| 认证客户优先 | 开关 | 开启后，已认证客户排序靠前 |
| 按认证类型筛选 | 多选 | 可选择只看"已通过身份认证"、"已通过学历认证"等 |
| 排除未认证客户 | 开关 | 开启后，完全排除无任何认证的客户 |

### 8.2 匹配引擎联动

认证状态不直接影响匹配分数计算，但影响推介决策：

- 已认证客户在推介时，红娘可以明确告知对方"该客户已通过 XX 认证"
- 匹配结果列表中，已认证客户可获得"已认证"标签加持
- 第一阶段不做"认证加权匹配分"，避免过早引入复杂度

### 8.3 认证作为销售工具

聚合版明确指出"认证是提升成交率的销售工具"。具体体现为：

- 红娘向客户推介时，已认证档案的说服力更强
- 红娘可以引导客户完成认证，作为服务增值点
- 认证完成度可以作为红娘 KPI 的参考指标之一

## 九、认证数据安全与隐私

### 9.1 材料存储安全

- 认证材料必须加密存储
- 认证材料的访问必须有权限控制
- 身份证号码等敏感信息不作为正式字段存储在 `customer_profile` 中
- 认证材料的下载/查看必须记录操作日志

### 9.2 材料展示脱敏

- 身份证照片在审核界面展示时，身份证号码中间部分应打码
- 收入证明中的银行账号应打码
- 对客资料卡只展示认证结论标签，不展示任何材料内容

### 9.3 材料保留策略

- 认证通过后，材料保留用于争议追溯
- 客户退档后，认证材料保留期限遵循法律要求（建议至少 3 年）
- 客户主动要求删除时，需评估法律合规后处理

## 十、与现有冻结文档的兼容确认

### 10.1 与字段冻结的兼容

- 认证不新增 `customer_profile` 字段
- 认证关联的字段（如 `education_level`、`marital_history`）只做校验参考，不反向覆盖
- 认证状态不进入字段字典的 `P0-P3` 分层，独立在 `P4` 层

### 10.2 与主数据模型的兼容

- 认证对象仍为 `profile_certifications`，不新增顶层对象
- 认证材料引用仍通过 `material_refs` 指向 `profile_materials.supplemental_materials`
- 认证审核日志第一阶段先用 `reviewed_at / reviewed_by / review_notes` 承接

### 10.3 与导入/资料卡冻结的兼容

- PDF 导入中的证书类材料，进入 `supplemental_materials`，`kind = document`
- 资料卡三版本的认证展示规则，遵循本文第七节定义
- 认证材料不等于认证结论，这一边界继续保持

3. 审核流程有明确的角色分工和最小能力要求

## 十二、当前结论

基于聚合版 `2.4` 的原始需求和已冻结的数据模型，我当前的完整理解是：

1. 认证体系不只是"防投诉"，更是提升成交率的销售工具和信任基础设施
2. 五级认证的核心不是"等级高低"，而是"不同业务场景需要不同类型的信任验证"
3. 认证审核必须由人工完成，第一阶段不做 AI 自动审核
4. 认证状态是独立维度，不应与客户档案字段混淆
5. 第一阶段的重点是把认证对象结构和审核最小流程跑通，不追求自动化和智能化
