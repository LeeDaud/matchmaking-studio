## 一、这份文档解决什么问题

聚合版 `2.5` 提出了三种数据导入通道（PDF 拖入识别、录音转写+字段提取、微信截图识别），导入与资料卡冻结 v1 已经定义了三入口的字段落点规则和 AI 草稿流转机制。但当前主线还缺一份从产品视角出发的、覆盖完整用户操作流程的详细需求方案。

这份文档的作用是：

1. 把三种导入通道的完整用户操作流程写清楚
2. 明确每种通道的输入格式、解析策略、字段映射规则和异常处理
3. 明确三通道共享的 AI 草稿 → 人工确认 → 正式写入流转的产品交互
4. 明确第一阶段各通道的实现优先级和最小可用范围
5. 明确与已冻结文档的对齐关系，不重复定义已有规则

一句话：

**本文不是再重复"要做导入"，而是把聚合版 `2.5` 和已冻结的导入规则细化成当前主线可执行的产品流程方案。**

## 三、总体原则

### 3.1 三通道共享同一套字段落点

无论从哪个通道进入，最终的字段落点必须以冻结字段字典为准。不允许任何通道自己发明中间字段或内部 key。

### 3.2 AI 提取结果一律先进草稿层

所有非手动确认的字段值，统一先形成 `field_observations`（草稿层），经人工确认后才进入正式对象。这是已冻结的核心规则。

### 3.3 导入是"辅助录入"，不是"替代录入"

导入通道的目标是减少红娘手动录入的工作量，但不能替代红娘的判断。AI 提取的结果必须经过人工确认才能成为正式值。

### 3.4 降级优于失败

当 AI 提取失败或置信度过低时，应降级为"材料留存 + 人工处理"，而不是直接报错丢弃。

## 四、通道一：PDF 拖入识别

### 4.1 适用场景

- 红娘收到客户的 PDF 格式个人资料
- 红娘收到其他机构转来的客户档案 PDF
- 红娘将纸质资料扫描成 PDF 后导入

### 4.2 支持的 PDF 类型

| PDF 类型 | 第一阶段支持 | 说明 |
|------|------|------|
| 文本型 PDF（可选中文字） | 是 | 直接提取文本内容 |
| 扫描型 PDF（图片） | 是（降级） | 先 OCR 再提取，准确率较低 |
| 加密 PDF | 否 | 提示用户先解密 |
| 多页 PDF | 是 | 逐页解析，合并结果 |

### 4.3 用户操作流程

```
步骤 1：红娘在客户详情页或建档页点击"导入资料"
  ↓
步骤 2：选择"PDF 导入"，拖入或点击选择 PDF 文件
  ↓
步骤 3：系统上传文件，显示"正在解析..."
  ↓
步骤 4：解析完成，系统展示"字段提取结果预览"
  - 左侧：PDF 原文预览
  - 右侧：提取出的字段列表，每个字段显示：
    - 字段名（中文）
    - 提取值
    - 置信度标识（高/中/低）
    - 原文出处高亮
  ↓
步骤 5：红娘逐项确认或修改
  - 可单个确认
  - 可批量确认（高置信度字段）
  - 可修改后确认
  - 可忽略某个字段
  ↓
步骤 6：确认完成，字段写入正式对象
  - PDF 原文件保存到 supplemental_materials（kind = document）
```

### 4.4 字段映射规则

PDF 解析层必须输出标准化的字段映射结果，格式为：

```ts
Array<{
  field_key: string          // 冻结字段字典中的 key
  extracted_value: string    // 提取的原始值
  normalized_value: any      // 标准化后的值（枚举转换、单位换算等）
  confidence: number         // 0-1 置信度
  evidence_text: string      // 原文出处
  page_number: number        // 所在页码
}>
```

映射目标必须以冻结字段字典为准：

- 如果 PDF 中出现"姓名：张三"，映射到 `full_name`
- 如果 PDF 中出现"学历：硕士"，映射到 `education_level = master`
- 如果 PDF 中出现"月薪：2万"，映射到 `monthly_income = 20000`
- 如果 PDF 中出现无法映射的内容，先落入对应对象的 `notes` 备注字段

### 4.5 常见 PDF 格式的字段映射表

基于聚合版中"客户信息登记表（微信简写版）"的字段，定义标准映射：

| PDF 中的常见标签 | 映射目标字段 | 转换规则 |
|------|------|------|
| 姓名 / 中文全名 | `full_name` | 直接映射 |
| 出生年月 | `birth_year_month` | 转为 `YYYY-MM` 格式 |
| 星座 | `zodiac_sign` | 映射到标准枚举（系统派生，可校验） |
| 身高 | `height_cm` | 提取数值，单位统一为 cm |
| 体重 | `weight_kg` | 提取数值，单位统一为 kg |

| 毕业院校 | `bachelor_school`（默认） | 需结合学历判断归属 |
| 专业 | `major` | 直接映射 |

| 工作单位 | `company_name` | 直接映射 |

| 是否有子女 | `has_children` | 映射到 yes/no/unknown |
| 手机 / 移动电话 | `phone` | 直接映射 |
| 微信 | `wechat_id` | 直接映射 |
| 兄弟姐妹 | `siblings_summary` | 直接映射文本 |
| 父母职业 | `parents_occupation` | 直接映射文本 |
| 父母婚姻 | `parents_marital_status` | 映射到标准枚举 |
| 家庭总资产 | `family_asset_band` | 映射 A7/A8/A9/A10 |
| 性格 | `personality_summary` | 直接映射文本 |
| MBTI | `mbti` | 映射到标准 16 型 |
| 兴趣爱好 | `hobbies` | 尝试拆分为标签数组 |

| 择偶-年龄范围 | `preferred_age_min` + `preferred_age_max` | 拆分区间 |
| 择偶-身高范围 | `preferred_height_min` + `preferred_height_max` | 拆分区间 |

### 4.6 异常处理

| 异常情况 | 处理方式 |
|------|------|
| PDF 无法解析 | 提示"文件格式不支持"，文件仍保存到 supplemental_materials |
| 解析结果为空 | 提示"未能识别有效信息"，文件保存，建议手动录入 |
| 部分字段置信度过低 | 低置信度字段标记为"待确认"，不自动进入批量确认 |
| PDF 内容与已有客户信息冲突 | 按冻结的冲突保护规则处理，展示冲突对比 |
| 文件过大（>20MB） | 提示压缩后重试 |

## 五、通道二：录音转写+字段提取

### 5.1 适用场景

- 红娘与客户通话后，上传通话录音
- 红娘与客户面谈后，上传现场录音
- 系统集成电话系统后，自动获取通话录音

### 5.2 支持的音频格式

| 格式 | 第一阶段支持 | 说明 |
|------|------|------|
| MP3 | 是 | 最常见格式 |
| WAV | 是 | 无损格式 |
| M4A | 是 | iPhone 录音默认格式 |
| AMR | 是 | 微信语音常见格式 |
| OGG | 否（第一阶段） | 后续支持 |

### 5.3 用户操作流程

```
步骤 1：红娘在客户详情页点击"导入资料" → 选择"录音导入"
  ↓
步骤 2：上传录音文件（拖入或点击选择）
  ↓
步骤 3：系统上传文件，显示"正在转写..."
  - 预估时长提示（如"预计 2-3 分钟"）
  - 支持后台处理，红娘可先做其他事
  ↓
步骤 4：转写完成，系统展示"转写文本 + 字段提取结果"
  - 上方：完整转写文本（可折叠）
  - 下方：提取出的字段列表，格式同 PDF 导入
  - 每个字段标注原文出处（点击可跳转到转写文本对应位置）
  ↓
步骤 5：红娘逐项确认或修改（交互同 PDF 导入）
  ↓
步骤 6：确认完成，字段写入正式对象
  - 录音文件保存到 supplemental_materials（kind = voice_note）
  - 转写文本保存到 supplemental_materials（kind = document）
```

### 5.4 转写质量要求

| 指标 | 第一阶段要求 | 说明 |
|------|------|------|
| 中文识别准确率 | ≥ 90% | 普通话场景 |
| 方言支持 | 不要求 | 第一阶段只支持普通话 |
| 多人对话区分 | 建议支持 | 区分红娘和客户的发言 |
| 时间戳 | 建议支持 | 方便定位原文出处 |
| 最大录音时长 | 120 分钟 | 超长录音提示分段上传 |

### 5.5 字段提取策略

录音转写后的字段提取，与 PDF 共享同一套字段映射目标，但有以下特殊规则：

| 规则 | 说明 |
|------|------|
| 对话语境理解 | AI 需要理解对话上下文，而不是逐句提取关键词 |
| 多轮确认优先 | 如果客户在对话中多次提到同一信息且前后不一致，以最后一次明确表达为准 |
| 红娘复述优先 | 如果红娘复述确认了某个信息（如"您说您身高 175 对吧"），以复述确认值为准 |
| 模糊表达降级 | 如果客户表达模糊（如"收入还行"），不强行提取数值，标记为低置信度 |
| 敏感字段保守 | 婚育、收入等敏感字段，只在客户明确表达时才提取 |

### 5.6 异常处理

| 异常情况 | 处理方式 |
|------|------|
| 录音质量差（噪音大） | 提示"录音质量较低，识别结果可能不准确"，仍尝试转写 |
| 转写结果几乎为空 | 提示"未能识别有效语音内容"，录音文件仍保存 |
| 转写超时 | 提示"处理时间较长，完成后将通知您"，转为后台任务 |
| 提取字段与已有信息冲突 | 按冻结的冲突保护规则处理 |
| 文件格式不支持 | 提示支持的格式列表 |

## 六、通道三：微信截图识别

### 6.1 第一阶段定位

导入与资料卡冻结 v1 已明确：微信截图识别作为第四入口预留，第一阶段不强制实现识别提取，但字段落点规则与前两个入口保持一致。

第一阶段的最小实现：

- 支持上传截图到 `supplemental_materials`（`kind = screenshot`）
- 不要求实现 OCR 识别和字段提取
- 预留识别接口，后续可接入

### 6.2 适用场景（完整方案，供后续实现参考）

- 客户通过微信发来的个人介绍文字截图
- 客户朋友圈截图
- 客户发来的证件照片
- 其他社交平台的个人资料截图

### 6.3 完整用户操作流程（后续实现）

```
步骤 1：红娘在客户详情页点击"导入资料" → 选择"截图导入"
  ↓
步骤 2：上传截图（支持多张，拖入或点击选择或粘贴）
  ↓
步骤 3：系统上传文件，显示"正在识别..."
  ↓
步骤 4：识别完成，展示提取结果
  - 左侧：截图原图
  - 右侧：提取出的字段列表
  ↓
步骤 5：红娘确认或修改（交互同 PDF 导入）
  ↓
步骤 6：确认完成，字段写入正式对象
  - 截图保存到 supplemental_materials（kind = screenshot）
```

### 6.4 第一阶段简化流程

```
步骤 1：红娘在客户详情页点击"上传截图"
  ↓
步骤 2：上传截图文件
  ↓
步骤 3：截图保存到 supplemental_materials（kind = screenshot）
  ↓
（无自动识别，红娘查看截图后手动录入相关字段）
```

### 6.5 截图类型与识别策略（后续实现参考）

| 截图类型 | 识别策略 | 难度 |
|------|------|------|
| 纯文字截图 | OCR + 字段提取 | 中 |
| 微信聊天记录截图 | OCR + 对话结构解析 + 字段提取 | 高 |
| 朋友圈截图 | OCR + 图文混排解析 | 高 |
| 证件照片 | 专用证件 OCR | 中 |
| 个人资料页截图 | OCR + 表单结构识别 | 中 |

## 七、三通道共享的确认交互

### 7.1 确认界面统一设计

无论从哪个通道进入，确认界面的交互应保持一致：

| 区域 | 内容 | 说明 |
|------|------|------|
| 原始材料区 | PDF 预览 / 转写文本 / 截图原图 | 左侧或上方 |
| 提取结果区 | 字段列表 + 置信度 + 原文出处 | 右侧或下方 |
| 操作区 | 逐项确认 / 批量确认 / 修改 / 忽略 | 每个字段行内操作 |
| 冲突提示区 | 与已有值冲突的字段高亮 | 需展示新旧值对比 |

### 7.2 置信度展示

| 置信度区间 | 展示标识 | 默认行为 |
|------|------|------|
| ≥ 0.9 | 高（绿色） | 可进入批量确认 |
| 0.7 - 0.9 | 中（黄色） | 建议逐项确认 |
| < 0.7 | 低（红色） | 必须逐项确认，不进入批量确认 |

### 7.3 高敏感字段的特殊处理

以下字段无论置信度多高，都必须逐项人工确认，不允许批量确认：

```
has_children
children_count
children_age_notes
custody_status
financial_ties_with_ex_partner
marital_history
monthly_income
annual_income
family_asset_band
financial_assets_notes
insurance_notes
appearance_score
```

（与导入冻结 v1 中的高敏感字段清单保持一致）

### 7.4 确认后的写入规则

- 确认的字段值进入正式对象，状态为 `confirmed`
- 忽略的字段值保留在 `field_observations`，状态为 `draft`
- 修改后确认的字段值，以修改后的值写入正式对象
- 原始材料文件始终保存到 `supplemental_materials`

## 八、第一阶段实现优先级

### 8.1 优先级排序

| 优先级 | 通道 | 第一阶段范围 | 理由 |
|------|------|------|------|
| P0 | PDF 导入 | 完整流程（上传 → 解析 → 确认 → 写入） | 覆盖最多实际场景，红娘手里大量 PDF 格式客户资料 |
| P1 | 录音导入 | 完整流程（上传 → 转写 → 提取 → 确认 → 写入） | 通话是红娘获取信息的主要方式 |
| P2 | 截图导入 | 仅上传留存，不做识别提取 | 识别难度高，先保证材料不丢失 |

### 8.2 第一阶段不做的

- 批量导入（一次导入多个客户的 PDF）
- 实时通话转写（需要电话系统集成）
- 微信截图 OCR 识别
- 导入历史记录和版本管理
- 导入模板自定义

### 8.3 第一阶段必须做的

- PDF 导入完整流程
- 录音导入完整流程
- 截图上传留存
- 三通道统一的确认交互
- 高敏感字段强制人工确认
- 冲突检测和保护
- 原始材料保存

## 九、本文对应的验收标准

1. PDF 导入的完整用户操作流程可直接指导交互设计和前端实现
2. 录音导入的完整用户操作流程可直接指导交互设计和前端实现

4. 三通道共享的确认交互规则统一且可执行
5. 字段映射表覆盖了聚合版中"客户信息登记表"的所有字段
6. 异常处理和降级策略完整，不会出现"导入失败且材料丢失"的情况
7. 与已冻结的三份文档（字段/数据模型/导入资料卡）无冲突

## 十、当前结论

基于聚合版 `2.5` 的原始需求和已冻结的导入规则，我当前的完整理解是：

1. 数据导入的核心价值是"减少红娘手动录入工作量"，不是"替代红娘判断"
2. 三通道必须共享同一套字段落点和确认流程，不能各自为政
3. AI 提取结果一律先进草稿层，人工确认后才成为正式值——这是不可动摇的底线
4. 第一阶段优先保证 PDF 和录音两个通道跑通，截图先做材料留存
5. 降级策略比完美识别更重要——宁可多一步手动确认，不能丢失客户信息
